# QR-06 — Recognition priority, guarded scheduling and benchmarking

Historical report: backups and experimental upload steps below refer to the
preserved standalone project, not the consolidated Git copy. Current development
uses [IoT-01 defaults and the consolidation guide](../../docs/iot-project-consolidation.md).
Fast experiments remain disabled; no hardware upload is authorized by consolidation.

## Evidence and current limits

QR-05 is preserved in `backups/before-qr-06/`. The user confirmed physical decoding, VGA snapshots, mode switching and roughly 8 FPS preview. No detailed physical QRTIME dataset accompanied this request. Consequently **no actual speedup, maximum safe scan rate, physical percentile or dominant CPU bottleneck is claimed**. Build/mocked tests do not replace those measurements.

Confirmed code-level bottlenecks:

- QR-05 waited on snapshotMutex before conversion/detection. The image sender holds that same lock for its full HTTP response, bounded at 1500 ms. Therefore a slow browser could hold up an actual QR attempt, despite separate camera ownership.
- QR-05 status polling awaited the image refresh, so a delayed picture could also delay notification of a ready decoded result.
- A fixed 100 ms worker-loop sleep added unnecessary scheduling overshoot after an attempt that had already overrun its scan interval.

Suspected until measured: framebuffer retrieval/driver waits, JPEG conversion, grayscale preparation, quirc identification and payload decoding. Original capture_ms includes a stale-buffer discard plus retrieval of another frame; it is NOT sensor exposure/acquisition time. The VGA sensor may have acquired some image data before esp_camera_fb_get returns. No exposure-duration measurement is invented.

## Exact changes

1. Optional snapshot publication uses a zero-wait cache-lock attempt. If an HTTP reader owns the image, skip publication and continue recognition; keep the previous cached image with its genuine age. This removes network wait from the scan hot path without another large image buffer. Cache copy remains a bounded optional operation before returning the framebuffer; it cannot queue behind HTTP. Other mode-change cleanup still waits safely for an outstanding bounded reader before freeing memory.
2. Snapshot publication is limited to at most once per 1000 ms, even in an enabled fast scan experiment. It remains independent from the scan floor; skipped snapshots are counted. The page may legitimately show older snapshots while recognition continues faster.
3. Schedule each next attempt against previous start time plus the selected minimum interval. Always yield at least 20 ms after over-budget processing; sleep in bounded increments while waiting. No concurrent scanner, spin loop, or watchdog disable is introduced. Failed capture/conversion retains conservative behavior.
4. Keep 1000 ms as default. Add an explicit opt-in 500 ms experiment, disabled in this build, and a runtime headroom gate. No 250 ms / 4 Hz experiment is implemented. Merely enabling detailed benchmark logging does not enable faster scanning.
5. Reuse the same decoder, VGA/JPEG/PSRAM workspaces, color conversion and average-channel grayscale algorithm. No new decoder or per-scan image allocation. Lower-resolution/raw-grayscale/multi-buffer changes are deferred: there is no measurement justifying risk to the proven QR readability.
6. QR result status polls every nominal 500 ms while in QR mode; Preview status remains 2000 ms. Image refresh stays separately throttled at 2000 ms with at most one in-flight image. One status request runs at a time, and stale status responses from before a mode request are discarded. New text can reach the page while an older image fetch is still outstanding.
7. Preserve last successful text and five-second repeat cooldown. Add event timestamp and attempt ID. The page displays reported event age plus the status request round trip; this is an approximate decode-event-to-notification indication, not synchronized-clock or physical presentation latency. Different decoded text still notifies immediately.

Remaining limitation: the page HTTP server itself handles requests synchronously, so a snapshot transfer can still delay a queued status response by its bounded send time. Scanner recognition no longer waits for that transfer. Removing HTTP head-of-line blocking would require more task/server complexity and is deferred until measured. Frontend concurrency is bounded to one status and one image, so it does not build growing request queues.

## Configuration before/after

| Setting | QR-05 | QR-06 shipped defaults |
|---|---|---|
| Preview | QVGA quality 15, 8 FPS cap | Unchanged |
| QR capture/decoder | VGA quality 12, one JPEG buffer, quirc | Unchanged |
| QR scan floor | 1000 ms | 1000 ms, configurable/gated experiment |
| Worker overrun yield | 100 ms loop sleep | Minimum 20 ms cooperative yield |
| Cache publication | Blocking lock, every scan | Nonblocking, at most once/1000 ms |
| QR status polling | Image-dependent, nominal 2 seconds | Image-independent, nominal 500 ms |
| Snapshot fetch | Nominal 2 seconds | Same throttle, one outstanding |
| Duplicate notification cooldown | 5000 ms | Unchanged |
| Wi-Fi, pins, endpoints, credentials | Working configuration | Unchanged |

Constants in src/main.cpp:

- QR_ENABLE_FAST_EXPERIMENT = false: do not edit until baseline logs show headroom.
- QR_EXPERIMENT_INTERVAL_MS = 500: experimental 2 attempts/s floor, not promised achieved throughput.
- QR_FAST_REQUIRED_SAMPLES = 20 and QR_FAST_HEADROOM_US = 350000: require consecutive complete processing attempts at or under 350 ms, free heap at least 65536 bytes and worker stack high-water mark at least 4096 bytes. An empty scene is still a processing sample; a successful QR payload is not required for the gate.
- A failure, slow attempt or memory/stack gate failure immediately selects 1000 ms again. Every mode session starts conservatively. Thresholds are conservative engineering gates, **not physical proof of sustained safety**; vary scene and QR complexity in acceptance tests.
- QR_BENCHMARK_LOG_EACH_SCAN = false: keep ordinary logging lightweight. Temporarily enable for distribution/throughput measurement.

QRPERF shows chosen interval, headroom sample count, completion-to-completion period, ready-result time and skipped cache publications. QRTIME retains all previous phase timings. If an operation never returns, its duration is not available yet. Existing memory/RSSI/capture-failure/send-timeout/reset diagnostics remain.

## Timing definitions

- capture_us / capture_ms: framebuffer retrieval path including the existing stale-frame discard; not sensor exposure duration.
- convert / gray / detect / decode: existing stage timers, same definitions as QR-05.
- total_us: scan start through existing bookkeeping and notification work, before optional benchmark logging.
- ready_us: attempt start to a successfully ready result; zero when none decoded. It is NOT time from a person's presentation of a code.
- completion-to-completion period and completed_ms: measure achieved scanner throughput, including pacing and previous log overhead.
- event_age_ms: age of the last notification event (not necessarily the latest repeated decode); preserved result is explicitly cached. Same-payload Serial messages may repeat after cooldown, but unchanged webpage text is not announced again.
- Browser snapshot timings and timestamps remain separate from recognition timings. Changing UI refresh cannot itself make the decoder faster.

## Three-code hardware benchmark

Prepare three high-contrast printed QR codes of identical physical size/print quality encoding `SMARTBARANGAY-TEST-A`, `SMARTBARANGAY-TEST-B`, and `SMARTBARANGAY-TEST-C`. Keep light, distance, lens focus, power, hotspot, browser/device and physical position constant between runs. Use a tripod/marked positions if available.

1. **Original QR-05 baseline:** restore the backup source temporarily, build/upload, and capture Serial logs including QRTIME/QRDIAG/DIAG. Use PlatformIO Monitor's log2file filter (for example `pio device monitor --port COM3 --baud 115200 --filter log2file`), or save monitor output manually. Record the filename; use the actual COM port. Do not modify secrets.h.
2. Run two minutes with no code, two minutes per stationary code, and at least 30 randomized A/B/C presentation trials (ten each). Remove the previous code completely before each presentation. Record presentation-to-first-correct-result latency with a video showing both presentation and Serial/web notification; use the same latency definition for both builds. Record timeout failures, for example no correct recognition within five seconds. A repeatedly decoded stationary QR is not a new presentation trial.
3. **QR-06 at stable floor:** restore the QR-06 source (save a local copy before testing the baseline), set QR_BENCHMARK_LOG_EACH_SCAN = true, leave QR_ENABLE_FAST_EXPERIMENT = false, build/upload and repeat the identical protocol. Save all QRBENCH and normal diagnostics. Logging itself adds some overhead; keep this in mind when comparing against the original sparse baseline logs.
4. Baseline QR-05's QRTIME lines are sparse last-attempt samples: they can support a clearly labelled sampled processing mean, not exact all-scan percentiles. Derive its achieved scan rate from differences in QRDIAG attempt counts divided by wall time, and its recognition latency/success rate from the controlled presentation trials. Do not fabricate full per-attempt distributions from sparse samples.
5. Only if QR-06 timing logs consistently show the configured headroom under no-code AND three-code scenes, plus stable memory/stack/decoding, explicitly enable QR_ENABLE_FAST_EXPERIMENT = true. Rebuild/upload and repeat. Its gate begins at 1000 ms and may select 500 ms after sufficient qualifying samples. Confirm QRPERF interval_ms actually changes; revert if failure rate, latency, memory, resets or timeouts worsen. Do not increase automatically to 4 Hz.
6. Add manual trial annotations to a COPY of each saved log, for example `[TRIAL] code=A success=1 latency_ms=<measured-value>` or `[TRIAL] code=B success=0`. Never insert guessed latency values.
7. Analyze a QR-06 detailed log: `python test/analyze_qr_benchmark.py <saved-log.txt>`. It reports mean processing, completion throughput by session, successful scan-to-ready median/p95 (nearest-rank), manual presentation-trial median/p95 and success counts, reset reasons and diagnostic ranges. For an empty scene, successful-decode latency is null. A log with no per-scan records is rejected rather than assigned invented statistics.
8. Inspect DIAG capture_fail, heap/PSRAM trend, RSSI and send_timeouts. Boot counts require manual classification into intentional versus unexpected resets. Compare values across equal-duration/equal-scene runs; no-code performance must be included.
9. Test Preview 8 FPS, Stop, repeated QR-to-Preview transitions, browser throttling/network loss and twenty-minute continuous QR operation. Slow/closed image clients may increase snapshots_skipped but must not create a scanner lock wait. Snapshot freshness must remain honest even when publication is skipped.

**Physical benchmark values are pending.** This change does not claim actual 2–4 Hz recognition, a new success rate, or a physically verified improvement.

Attempted passive hardware-log collection: PlatformIO detected one CH340 device at COM3. Opening COM3 at 115200 with DTR/RTS configured low failed with `PermissionError(13, Access is denied)`. No diagnostic samples were collected; another Serial Monitor may own the port. No upload, deliberate reset command or credential change was performed. Close the owning monitor before using a single logger for the benchmark. This is a concrete measurement blocker, not evidence of firmware failure.
