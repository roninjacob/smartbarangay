# QR-03 — Snapshot display and scanner usability

Historical report: recovery paths below refer to the preserved original standalone
project. Use the [consolidation guide](../../docs/iot-project-consolidation.md) for
current location and safe-default build instructions.

## Evidence and limits

User-reported physical QR-02 result: 96 attempts, five successful decodes including repeats, matching `SMARTBARANGAY-TEST-001`; text displayed correctly. VGA snapshots were broken and the page could remain on Switching to QR mode. These are user-provided hardware results, not a new test performed by the coding agent.

QR-03 preserves quirc sources, JPEG-to-grayscale conversion, camera pin mapping, Preview QVGA/quality 15/5 FPS, QR VGA/quality 12/roughly one scan per second, single preview viewer, Wi-Fi sleep disabled and 1500 ms image-send bounds. Private credentials and platformio.ini remain unchanged. No Laravel or reservation/check-in work is included.

## Confirmed code defects and suspected physical cause

1. `/qr/frame` waited only 50 ms for cameraMutex. The QR worker held that mutex across capture, JPEG conversion and the entire quirc detection/decode. Repeated lock contention could therefore produce repeated 503 image responses. This contention exists in code; actual hardware HTTP status traces were not available to prove it caused every failed image.
2. The image handler always returned ESP_FAIL even when httpd_resp_send completed successfully. That deliberately took the error/session-close path for every JPEG. HTTP Content-Type and Content-Length generation were otherwise appropriate. The browser-specific effect of that close was not measured, so it is a contributing suspicion, not a proven sole cause.
3. Browser code replaced img.src on every poll without checking response status/type or maintaining the last successfully decoded image. A 503, truncated body or decode failure could display a broken image.
4. Status polling read the actual mode but did not update the main mode message after the POST response. The stale Switching text is directly explained by this code.

## Changes

- Add snapshotMutex for cached JPEG allocation, publication, read and free. `/qr/frame` no longer acquires cameraMutex. QR decoding remains under the same camera ownership protection as before. The snapshot reader holds its own lock only during its bounded transfer; the worker holds it only while copying/freeing the cache. There is no reverse camera-lock acquisition by the image handler, avoiding a camera/snapshot lock cycle.
- Publish only bounded JPEG buffers with the SOI marker. Failed/oversized publications retain the previous valid cache. Actual JPEG validity is also checked by the browser decoder; SOI alone is not full validation.
- Successful image responses return their actual send result with HTTP 200, image/jpeg, Content-Length and no-store. After the bounded send, restore the ordinary page-session send callback so an expired snapshot deadline cannot poison the next keep-alive response. The ordinary writer retains the existing page socket timeout; MJPEG/snapshot sends keep their absolute deadline.
- Fetch each snapshot, check HTTP status and Content-Type, download the complete body with a four-second timeout, and decode a candidate image before replacing the displayed image. Polls are sequential. Preserve the last good image on transient error and show an explicit retry message. Revoke replaced/discarded blob URLs and abort in-flight images during mode changes/page exit.
- Update the mode message from server-confirmed mode on every poll; expose error separately from switching. Return to Preview cancels the snapshot and restarts MJPEG after the server reports preview mode.
- Put latest decoded text in a prominent, separate aria-live element. Update it only if displayed text changes; scan counters stay in a separate non-live details block. QR text remains plain text, never executable HTML or a navigation command.
- Preserve the existing five-second Serial repeat cooldown, add payload length to the hash comparison, and apply the same notification decision to result events. Raw successful-decode count still includes repeats. The new notification count is not a count of unique people/reservations. A different payload may notify immediately; identical payloads notify at most once per five seconds. Deduplication is a UX heuristic, not security validation.

## Physical test

1. Close old test tabs/Serial Monitor. Build/upload from this standalone project:

   ```powershell
   pio run -e esp32cam
   pio device list
   pio run -e esp32cam -t upload --upload-port COM3
   pio device monitor --port COM3 --baud 115200
   ```

   Substitute the actual COM port. Press RST and open the printed device IP. Hard-refresh the webpage so its new JavaScript is loaded.
2. Verify moving Preview video and the existing diagnostics. Enter QR mode; allow camera initialization. Main status should change from Switching to QR mode active.
3. Present the same dummy QR. Confirm correct text in Serial and in the large Latest decoded QR panel. Check that published snapshots increase and the VGA image/timestamp update. Repeats can increase raw decode count; the same payload must not generate more than one Serial notification per five seconds or repeatedly rewrite the live text announcement.
4. Move the code/hand and confirm snapshot motion approximately every two seconds plus processing/network time. A snapshot is not a smooth video stream. Temporary errors should keep the last good image and show retry text, not a broken-image icon.
5. If images still fail, inspect `/qr/frame` in browser Network tools: expect HTTP 200, image/jpeg and a complete nonzero JPEG. Open `http://<device-IP>/qr/frame` directly as an additional check. Record any HTTP 503, network truncation, decode error, or send timeout. `/qr/status` remains available with mode, counters, payload and events.
6. Return to Preview after multiple successful scans. Verify MJPEG restarts without resetting the board. Repeat at least ten QR/Preview cycles and monitor heap/PSRAM recovery, capture failures and send timeouts. Decoder workspaces/cache should be released on preview return.
7. Leave QR mode running 20 minutes, test repeated/different dummy payloads, and record any remaining image or return-to-preview failure with diagnostics. Only then mark the snapshot/reliability fix physically verified.
