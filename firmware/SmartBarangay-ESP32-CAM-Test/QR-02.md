# First QR feasibility enhancement

Historical report: recovery paths below refer to the preserved original standalone
project. For current location, safe defaults and rollback boundaries, read the
[consolidation guide](../../docs/iot-project-consolidation.md).

## Scope and evidence

The user confirmed that the prior stability firmware streams continuously with improved RSSI (approximately -25 to -29 dBm) and no recent send timeouts. That firmware was backed up in `backups/before-qr-02/` before editing. Higher RSSI improves the link but cannot correct optical focus, motion blur or insufficient pixels per QR module.

This change implements on-device QR decoding and local display. Physical QR scanning and mode-switch stability remain UNVERIFIED until tested on the board. No Laravel/reservation validation is implemented. No credentials were changed; a SHA-256 comparison confirmed the private header was unchanged. No firmware was uploaded by the agent.

## Modes

| Setting | Preview | QR test |
|---|---|---|
| Resolution | QVGA 320x240 | VGA 640x480 |
| Sensor output | JPEG | JPEG |
| JPEG quality | 15 | 12 |
| Frame buffers with PSRAM | Two / LATEST | One / WHEN_EMPTY |
| Without PSRAM | Existing one-buffer QVGA fallback | Refused; preview remains available |
| Capture pacing | At most 5 FPS | Roughly one scan per second, slower if capture/decode/send is busy |
| Browser image | Existing live MJPEG | Latest captured JPEG snapshot, requested about every 2 seconds |
| Image send bound | Existing 1500 ms/frame | 1500 ms/snapshot |
| Wi-Fi modem sleep | Disabled | Disabled |

Preview sensor settings and send protections are preserved. The webpage avoids enlarging the QVGA preview above its native 320px width; QR snapshots display at up to 640px. This prevents needless display upscaling, not optical blur.

The camera is deinitialized/reinitialized under a mutex during mode changes. Raising the resolution only via sensor settings on the original QVGA buffers could exceed the expected buffer allocation; reinitializing allocates the correct buffers. Mode switching closes the preview stream after its current bounded send. The QR worker and streaming handler never acquire frames concurrently. Snapshots use the worker's cached JPEG, not a second capture task.

QR mode stays JPEG rather than capturing VGA raw RGB/grayscale over the ESP32 camera bus. The bundled converter produces RGB in PSRAM; software averages channels into quirc's grayscale input. This adds CPU/memory work at a deliberately slow rate while keeping sensor transfers compressed. One old single-buffer frame is discarded before each scanned capture.

## Decoder choice and memory

Vendored `dlbeer/quirc` tag v1.2, commit `542848dd6b9b0eaa9587bbf25b9bc67bd8a71fca`, ISC license retained. Only its C decoder sources are built via `lib/quirc/library.json`. It supplies no camera task, networking or account integration, so the existing ownership model stays in control.

Local adaptation: quirc.c allocations use explicit PSRAM-capable allocators on ESP32. Non-ESP32 builds use the original allocator. Source provenance and changes are recorded in `lib/quirc/LOCAL-NOTES.md`. Upstream Git metadata was retained locally as `upstream-git-metadata/` and ignored, so this is a vendor source directory rather than an embedded Git repository.

QR-only dynamic allocations include a 921,600-byte RGB buffer, 307,200-byte grayscale image, quirc recognition/decode workspaces and a 131,072-byte JPEG cache. Those are freed when returning to preview. The worker has a 24,576-byte internal stack and sleeps when inactive; build RAM percentages do not include all runtime allocations. Failed allocation or QR camera initialization falls back to preview where possible. A total camera reinitialization failure requires correcting hardware/power and resetting.

## Local interface

- `http://<device-IP>/`: existing page, now with Enter QR test mode / Return to preview controls.
- `http://<device-IP>:81/stream`: existing preview MJPEG; returns 409 while QR mode is requested/active.
- `POST /mode?value=qr` or `POST /mode?value=preview`: requests an asynchronous mode change.
- `GET /qr/status`: local mode, attempt count, success count and last decoded result in JSON.
- `GET /qr/frame`: latest cached VGA QR capture; may return 503 while processing or before the first snapshot.

These routes are local hardware-test controls, not Laravel APIs. One preview viewer is still supported. QR mode is global to the board, so use one test page. The page polls status and the cached image; it retries explicit stream errors, not undetectable visual freezes.

Web output uses textContent, not HTML. The webpage caps rendered text at 1024 bytes; Serial outputs the full decoded payload. Control/non-ASCII bytes are displayed as `\xNN` to avoid log injection/encoding ambiguity. Use short ASCII payloads for the first milestone; general Unicode/ECI presentation is not implemented. A QR containing a URL is displayed as text and is not opened. Last successful text remains visible after the code leaves the scene, labelled accordingly. Repeated successful frames increment the decode count; identical Serial messages are suppressed for about five seconds. These counts are not unique reservations or check-ins.

Use synthetic, non-sensitive QR text such as `SMARTBARANGAY-TEST-001`; decoded data is intentionally visible to the local webpage and Serial Monitor. HTTP is unencrypted/unauthenticated for this LAN test. Do not expose the device publicly.

## Diagnostics and verification

Existing five-second metrics remain: MJPEG frames/FPS, capture average, send average/max, heap, PSRAM, RSSI, capture failures, stream disconnects and send timeouts. In QR mode, capture timings include the stale-frame discard and fresh acquisition; TX timings include snapshot responses. MJPEG frames/FPS naturally stop while QR mode runs. `[QRDIAG]` adds active/requested mode, QR attempts, successful decodes (including repeats) and worker stack free bytes. Preserve a healthy stack margin during real tests.

Final PlatformIO build: PASS (exit 0, 10.86 seconds). RAM: 62,104 / 327,680 bytes (19.0%). Flash: 1,117,525 / 3,145,728 bytes (35.5%). Runtime PSRAM workspaces and the task stack are additional to the static build RAM figure. Mocked webpage checks passed for preview start, switching/stream stop, QR snapshot display, safe text output, preview restart, Stop and page-exit cleanup. Compiled quirc symbols confirm use of PSRAM allocation APIs. SHA-256 checks confirmed platformio.ini and the private header remained unchanged. These are software checks, not proof of a physical QR decode.

## Upload and physical acceptance test

1. Close old camera tabs and serial monitors. Keep the existing stable power supply and hotspot; leave private credentials as configured.
2. In this project: `pio run -e esp32cam`, `pio device list`, then `pio run -e esp32cam -t upload --upload-port COM3`. Substitute the actual COM port.
3. Open `pio device monitor --port COM3 --baud 115200`, press RST, and confirm camera/PSRAM/IP diagnostics. The full PlatformIO executable fallback is in README.
4. Open the printed `http://<IP>/` on the same LAN. Verify preview motion for five minutes and no new send timeouts before switching modes.
5. Click Enter QR test mode. Allow a few seconds for the old stream to close, camera to reinitialize, and the first VGA snapshot. A brief blank/stopped image during switching is expected.
6. Present a simple black-on-white QR encoding `SMARTBARANGAY-TEST-001`. Confirm an updated VGA snapshot and increasing QR attempt count. Success requires an exact matching decoded payload in `[QR] Decoded ...` and the webpage. Capture real logs/screenshots; no success is pre-recorded.
7. Click Return to preview. Verify that moving MJPEG resumes, PSRAM workspaces are released and FPS returns near its previous range.
8. Repeat switching ten times. Observe heap/PSRAM recovery, stack margin, camera failures, disconnects and timeouts. Intended mode changes increase stream disconnects; sustained memory decline or new reset is a failure.
9. Run QR mode for 20 minutes and test no code, a rotated code, a different payload and a repeated payload. Record detection distance, lighting, decode latency and whether preview recovers afterward.

## Lighting, distance and focus

- Start with a short payload and a printed QR approximately 8–12 cm wide, including an intact white quiet zone. Avoid dense long URLs for the first test.
- Try distances around 20, 30, 40 and 60 cm; these are starting points, not guaranteed lens specifications. Keep the whole code in the VGA image and make each square/module occupy several pixels.
- Use bright, diffuse illumination. Keep camera/code stationary during capture. Avoid glare, harsh shadows and a dim or reflective phone screen. The built-in flash stays off.
- The OV2640 module is normally fixed/manual focus; this firmware does not add autofocus. If the VGA snapshot remains soft at every practical distance, inspect optical focus/lens condition. Power off before carefully adjusting a genuinely adjustable lens; do not force a glued lens or touch the ribbon while powered.
- If a code is located but ECC errors occur, improve focus, module size, lighting and angle before raising resolution again. More pixels do not fix a physically out-of-focus image.

## Rollback to the confirmed stable version

From this standalone project in PowerShell:

```powershell
Copy-Item -LiteralPath .\backups\before-qr-02\main.cpp -Destination .\src\main.cpp -Force
Copy-Item -LiteralPath .\backups\before-qr-02\README.md -Destination .\README.md -Force
pio run -e esp32cam -t clean
pio run -e esp32cam
pio run -e esp32cam -t upload --upload-port COM3
```

`platformio.ini` was unchanged. `secrets.h` is never restored/overwritten. The old main.cpp no longer includes quirc, so PlatformIO's dependency finder does not link it; the vendor folder may remain for a later retry. The new .gitignore metadata rule can stay safely in place. Restoring source alone does not alter firmware already on the board: rebuild/upload is required.
