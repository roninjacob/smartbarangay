# QR-05 — Measured QR responsiveness and snapshot freshness

Historical report: backup paths and restoration commands below belong to the
preserved original standalone project. Follow the [consolidation guide](../../docs/iot-project-consolidation.md)
and IoT-01 defaults for current development.

## Initial finding

The observed visual difference is expected: Preview is MJPEG capped at 8 FPS (125 ms), while QR mode deliberately starts scan attempts no faster than every 1000 ms and displays occasional cached VGA snapshots. QR mode is not live video.

Confirmed avoidable delay in existing code: the frontend awaited status download, snapshot download and image decode, then waited an additional 2000 ms. Thus the real polling period was `work time + 2000 ms`, not 2000 ms. Repeated downloads of the same cached capture also reset the displayed update timestamp, making old data appear newly captured.

Other candidate bottlenecks are not yet measured on this board: stale+fresh frame acquisition, snapshot-cache contention during HTTP transfer, JPEG conversion, grayscale conversion, quirc detection, and QR decoding. Snapshot publication can wait behind a bounded image send for up to roughly 1500 ms; whether this occurs materially requires hardware logs. Large decoded payload Serial output may also add time on notification frames. No camera, quirc, Wi-Fi or scan-rate tuning has been applied based on guesses.

## Measurements added (actual values require running this build)

Every approximately five seconds `[QRTIME]` reports the LAST completed attempt, not a fabricated estimate or a window average:

| Field | Measures |
|---|---|
| samples | Number of completed timed attempts since boot, including failed conversion/capture attempts |
| last_lock_ms | Wait to acquire camera ownership |
| capture_ms | Existing stale-frame discard plus fresh framebuffer acquisition |
| cache_wait_ms | Wait for snapshotMutex before publishing |
| copy_ms | Copy into the existing JPEG cache and publish metadata |
| convert_ms | Bundled JPEG-to-RGB conversion |
| gray_ms | Existing RGB-to-grayscale loop |
| detect_ms | quirc image identification (quirc_end) |
| decode_ms | Code extraction/decode attempts including existing mirror retry; zero if no code was located |
| total_ms | Attempt time including locks, bookkeeping and any existing notification output |
| start_period_ms | Actual start-to-start scan interval; zero on the first attempt of a mode session |

Existing `[DIAG]` and `[QRDIAG]` remain available. QRTIME values persist as the last completed sample even when back in preview; they are not current preview timings. While an operation is blocked, its final duration is not available until it returns. No sample line is printed before the first completed timed attempt.

Browser text measures snapshot fetch/body download time, image decode time and total refresh time using performance.now(). These are browser-side timings; they must not be confused with camera/quirc timings. Firmware and browser clocks are not synchronized.

## Minimal changes and preserved behavior

- Keep Preview at 8 FPS, QVGA JPEG quality 15. Keep QR at VGA JPEG quality 12, approximately one attempt per second, with the existing quirc algorithm, duplicate cooldown and camera ownership. The previous 1000 ms literal is now named QR_SCAN_INTERVAL_MS with the same value.
- Add fixed-size timing counters; reuse existing result mutex for short copies. No new decoder, image workspace or camera task. Existing image memory ownership and bounded transfers are unchanged.
- Align browser polling to the nominal two-second start-to-start period by subtracting work time. Requests remain sequential; if processing exceeds the budget, wait at least 250 ms before the next cycle. This removes extra frontend waiting without increasing camera scanning frequency.
- Add capture sequence to status. Fetch an image only if a different capture is published. Add matching sequence and age headers to the JPEG response under snapshotMutex, so metadata belongs to the image actually sent.
- Show Scanning... while QR mode is active, with processing/waiting state, and a clear success message when a different decoded payload reaches the page. Same-payload notifications remain suppressed as before. The latest successful payload remains displayed when the code leaves the scene.
- Show frame number, last image-update timestamp and approximate image acquisition age. The age increases independently once a second; unchanged captures do not reset the timestamp. Mark images STALE after five seconds. The threshold is an informative UI label, not a new camera timeout or automatic restart.
- Keep the existing checked JPEG loading, last-valid-image retention, cancellation, blob cleanup, Preview return and all endpoints.

Age is measured from when the firmware obtains the frame, not the optical exposure timestamp. Browser age conservatively includes the refresh duration and is explicitly approximate. It is not an end-to-end latency measurement.

## Scan-rate decision

Leave QR_SCAN_INTERVAL_MS at 1000. No actual phase measurements are available yet to justify a shorter interval. If measured total processing already approaches/exceeds that budget, reducing it would increase load without necessarily increasing useful throughput. If measurements later show ample headroom, stable memory, low cache wait and unchanged decode reliability, a separate controlled experiment can be proposed. This build does not perform it automatically.

## Hardware acceptance and interpretation

1. Use the same known-good power supply/hotspot. Close old tabs, confirm the COM port, then:

   ```powershell
   pio run -e esp32cam
   pio run -e esp32cam -t upload --upload-port COM3
   pio device monitor --port COM3 --baud 115200
   ```

   Substitute the actual port, press RST and hard-refresh the device page.
2. Run Preview five minutes: check that approximately 8 FPS and stable send-timeout/memory behavior remain.
3. Enter QR mode. Record at least ten QRTIME lines without a code, then with the known dummy code, then different codes. Also record browser refresh timings, RSSI, memory, capture failures and timeouts. Label conditions; do not average values from unrelated conditions blindly.
4. Compare capture, cache wait, conversion, detection and decode times. A large cache_wait_ms points to publication blocked by an image transfer; large convert/gray/detect/decode values point to processing costs. start_period_ms greater than 1000 is expected when work overruns the pacing budget. total_ms can exceed summed phase values due to existing bookkeeping/notification output.
5. Confirm the page explicitly shows snapshots rather than a live-video claim. Frame IDs and update timestamps should advance only on new displayed captures. Observe a static scene: even if the pixels look identical, newly acquired frames should have new sequence numbers.
6. Temporarily interrupt the network while leaving the page open. Last image may remain, but its age must grow and become STALE instead of receiving a fresh timestamp. Reconnect and verify a new image advances the frame ID and timestamp. Do not intentionally unplug/power-cycle hardware while touching the camera ribbon.
7. Present a new dummy payload: check the success message and exact text. Present it repeatedly: cooldown and no repeated live-text rewrites should remain. Check that Scanning... remains distinct from last successful result.
8. Return to Preview and repeat ten QR/Preview cycles. Confirm decoding, snapshots and 8 FPS streaming still work, with no unexpected reset or sustained memory decline.
9. Run for 20–30 minutes, retain logs/screenshots, and compare the UI experience with the backup version. Only actual measurements establish improvement and the dominant device bottleneck.
