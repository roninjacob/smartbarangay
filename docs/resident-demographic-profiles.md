# Milestone 3: demographic profiles and existing PDF field mapping

## Profile contract

`resident_profiles` has a unique User foreign key, a nullable date `birthdate`,
and nullable plain-text fields: civil status (80), occupation (120), street (255),
zone/purok (120), emergency contact name (255), emergency contact number (30).
The User relationship is `profile()`. No existing User address or historical
reservation is overwritten or backfilled. The FK restricts account deletion;
stale-unverified cleanup explicitly preserves users with demographic profiles,
including in dry-run results.

The Resident Profile / Account Settings page displays the Bootstrap form; it is
not shown on the dashboard. Saves and validation errors return to that profile
page. `PUT /resident/profile/demographics` requires an active,
verified Resident, CSRF and the existing session lock. It uses the authenticated
owner only, rejects extra identity/authorization fields and validates every
submitted field server-side. Fields are optional and blanks become NULL.
Birthdates must be real formatted dates not later than the Philippine date;
contact numbers use the existing Philippine contact validator. Civil status is
bounded plain text, not a new eligibility rule or an unapproved status taxonomy.

Each write locks the parent User row, rechecks role/activation/verification, then
locks or creates that user's profile. This is the same parent serialization
used by final reservation submission. Unique `user_id` prevents a second profile.
Visits do not create a row, and no demographic data is exposed on the public page.

## Existing engine integration

The existing system-field registry, designer labels, sample values and field-form
guidance expose:

| System field | Source | Type |
| --- | --- | --- |
| `resident_birthdate` | profile birthdate, `Y-m-d` | Date |
| `resident_civil_status` | civil status | Text |
| `resident_occupation` | occupation | Text |
| `resident_address_street` | street | Text |
| `resident_address_zone_purok` | zone/purok | Text |

`resident_address` still comes from the existing account address. Emergency
contacts remain private profile fields and are not included in the document
mapping or reservation Resident snapshot. Missing demographic values are NULL;
the existing configured required/optional field validation remains authoritative.

`ReservationDocumentInformation::profile()` queries the profile afresh, including
when the final submission holds its parent User lock. New values flow through
the existing wizard review checks, Resident snapshot, answer/field/layout
snapshots, preserved PDF source, canonical preview and exact-byte finalization.
Later profile edits cannot replace historical values. A changed demographic
profile invalidates the reviewed wizard profile for a dynamically configured
request through the existing re-review rule.

Admins explicitly place new fields using normal versioned layout updates. No
existing configuration or placement is automatically changed. A pre-migration
inspection found no custom fields colliding with these five system names in
the current local database; deployment to another database must repeat that check.
Bracketed labels are not literal PDF/DOCX replacement tokens: the current engine
draws mapped text at saved PDF coordinates.

## Printing and scope

FPDI rendering, canonical preview review rules, generated-document serving,
`admin/certificates/print.blade.php`, print CSS and PDF.js printing logic are
unchanged. Source page sizes and historical generated bytes are preserved.
The only designer JavaScript change adds sample text for the five new fields;
no builder algorithm is rewritten. Printing remains separate from status,
payment, check-in and QR consumption.

## Account onboarding and request guidance

Registration stays unchanged in its data requirements: existing name, email,
password, contact and address fields only. It explains the next steps instead
of collecting demographics or emergency contacts during registration.

A Resident's first successful signed email verification redirects to Profile /
Account Settings with a one-time guidance message. Admin verification and normal
login destinations are unchanged. Reopening an already-used valid verification
link is idempotent and returns to the usual dashboard; it does not create a
profile-completion redirect loop. No global mandatory completion gate or
arbitrary completion percentage is introduced.

The selected document determines required system information. Missing required
values are listed beside a profile-edit link; the Continue action is disabled
while they are missing, and existing server validation independently rejects a
forged submission. Optional missing fields do not block the request. The profile
page offers Return to document form only for the authenticated Resident's own
wizard draft, using a fixed internal route rather than a client-supplied return
URL. Without an owned draft it offers Start a document request. Saving does not
submit a reservation or silently finalize the draft; the Resident reviews it
again under the existing profile/configuration freshness checks.

## Local rollout and verification

Migration `2026_10_25_000027_create_resident_profiles_table.php` ran in batch 20
after a verified SQL backup. Existing business-row fingerprints across 20 tables
matched before and after. The new table was left empty; no real profile fixtures
were saved. The backup is database-only and has no restore rehearsal.

Isolated tests cover create/update, validation and escaping, ownership/role and
CSRF protection, optional NULL values, legacy address preservation, private
emergency contacts, parent-lock ordering and historical PDF generation. SQLite
tests observe the actual query builder lock flag and transaction at profile
write time; they do not claim a simultaneous MariaDB stress test. End-to-end
coverage submits a configured request, edits the profile, verifies old placements
and promotes the exact reviewed PDF bytes through the unchanged finalizer.

Resident Profile / Account Settings browser checks at 1440, 768, 390 and 320
pixels found no page-level horizontal overflow. The dashboard no longer contains
the demographic form. No real profile was submitted during browser QA.

The profile-placement baseline passed: 1,061 PHP tests / 10,604 assertions, with
74 focused profile/Admin-profile/dashboard tests / 568 assertions.
The onboarding follow-up passed: 1,065 PHP tests / 10,657 assertions; 82 focused
profile/document/authentication tests / 905 assertions; and 70 focused cleanup,
verification and profile tests / 722 assertions. Registration guidance was also
checked at 320 pixels with no horizontal overflow. No additional migration was
needed for onboarding, and no real account or profile was created by browser QA.
All 19 JavaScript tests, Vite build, targeted Pint, route and diff checks passed.
Two earlier overlapping PHP runs collided in Laravel's shared fake-storage
directory; subsequent suites were run serially. No application printing or
upload behavior was weakened to accommodate those test-environment collisions.
