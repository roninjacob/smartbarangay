# Service fees — Phase 11A

`services.fee_amount` is the current fee source of truth. Admins must explicitly enter a fee in Create/Edit Service. Plain non-negative amounts with at most eight whole digits and two decimal places are accepted: 0.00 through 99,999,999.99. Commas, currency symbols, exponent notation, negatives and excess precision are rejected. Storage is nullable DECIMAL(10,2), with Laravel decimal string casts; formatting groups string digits without floating-point arithmetic.

NULL means a service has not been configured, or a historical reservation fee was not recorded. It never means free. An explicit 0.00 means free and is displayed consistently as ₱0.00. Existing rows are not backfilled. Admin catalog/edit screens identify services needing fee setup. New requests for an unconfigured service are blocked, including direct selection and final submissions from old drafts.

The Resident wizard shows the current fee during service selection and document/requirements review, and the reviewed fee on confirmation. The offered and reviewed amounts are server-owned session values, not submitted monetary inputs. A changed fee invalidates later wizard confirmation and returns the Resident to review the current amount and select a schedule again. Current decimal strings are compared at intermediate steps and inside the existing final Service/Schedule transaction locks.

Successful submission assigns `reservations.fee_snapshot` from the locked authoritative Service after the reviewed-fee comparison. It is nullable DECIMAL(10,2) and deliberately excluded from reservation mass assignment. Admin/Resident historical details use only this snapshot. Later service edits never update it; legacy NULL snapshots display “Not recorded”. Failed/stale submissions do not persist reservations, answers, attachments or source copies.

The forward migration `2026_10_16_000019_add_service_fees_and_reservation_fee_snapshots.php` adds the two nullable columns without defaults or data updates. Apply to real MySQL only after user review/authorization and backups; implementation tests apply it only to isolated SQLite. After migration, explicitly configure each applicable Service through Edit Service before accepting new requests. Until migration, fee writes require the missing columns and must not be attempted against real data.

Phase 11A records fees, not payments. No payment/receipt tables, payment methods, collection reports, payment status gates, PDF access restrictions, discounts, refunds, or payment history are implemented. Fee values are not inserted into document snapshots or certificate PDFs. Phase 10 rendering, review evidence, finalization, printing, historical sources, QR consumption, reservation transitions and date_issued retain their existing rules.
